  Adicione uma especificação OpenAPI e ganhe uma referência de API nativa, com uma página real por operação, na sua barra lateral e na busca.
---

Aponte o Blume para uma especificação OpenAPI e ele gera uma referência de API nativa: uma **página real por operação**, agrupada por tag em uma barra lateral com escopo de aba, com tabelas de schema, exemplos de requisição/resposta, exemplos de código gerados e um painel interativo [Try it](#try-it-playground). Como cada operação é uma página genuína do Blume, ela ganha sua própria URL, aparece na **busca do site** e no `llms.txt` e ganha uma imagem Open Graph, igual a qualquer documento escrito à mão.

Toda referência é um **adaptador** importado de `blume/reference` e listado em `reference`: `openapi()` para um documento OpenAPI, [`asyncapi()`](/docs/references/asyncapi) para um documento AsyncAPI e [`graphql()`](/docs/references/graphql) para um schema GraphQL. Cada adaptador cuida das próprias fontes de especificação, da própria rota de montagem e das próprias opções de exibição, então a lista pode ter quantos adaptadores de cada tipo você precisar. Como exemplo, a configuração abaixo aponta o Blume para a especificação pública do Petstore.

```ts blume.config.ts lineNumbers
import { defineConfig } from "blume";
import { openapi } from "blume/reference";

export default defineConfig({
  reference: [
    openapi({ spec: "https://petstore3.swagger.io/api/v3/openapi.json" }),
  ],
});
```

Isso monta a referência em `/reference` (uma página de visão geral), com cada operação em `/reference/<tag>/<operation>`. O `spec` pode ser uma URL `http(s)` ou o caminho de um arquivo local no seu projeto. O Blume faz o parse dele com o [parser de OpenAPI do Scalar](https://github.com/scalar/scalar). Especificações Swagger 2.0 e OpenAPI 3.0 são convertidas para 3.1 automaticamente, e especificações 3.1 e [3.2](#openapi-32) são lidas do jeito que foram escritas. Um adaptador é uma descrição simples da referência, e não uma especificação já processada. Por isso o Blume consegue validá-lo de antemão e embuti-lo no site gerado. Se você deixar `reference` de fora (ou vazio), nenhuma referência é renderizada. Está documentando uma API orientada a eventos ou uma API GraphQL? Veja [AsyncAPI](/docs/references/asyncapi) e [GraphQL](/docs/references/graphql).

A referência não adiciona uma aba ao cabeçalho sozinha. Para exibi-la, aponte uma [aba de navegação](/docs/content/navigation#tabs) para a rota dela. Isso também define o escopo da barra lateral de operações no renderizador nativo:

```ts blume.config.ts
navigation: {
  tabs: [{ label: "API", path: "/reference" }],
}
```

Os grupos de tags da barra lateral e as seções da página de visão geral seguem a mesma ordem: a ordem da lista `tags` na raiz da especificação e, depois, qualquer tag que ela não declare, na ordem em que as operações a usam pela primeira vez.

:::note
As operações são indexadas para busca pelo **resumo, pela descrição, pela tag e pelo endpoint** (`GET /pets/{id}`). As tabelas de schema renderizadas e os exemplos de código gerados não passam por indexação de texto completo. A busca encontra o título, a prosa, a seção e o caminho de uma operação e depois leva você à página dela. [Seus próprios exemplos](#your-own-samples) são indexados como qualquer bloco de código, mas só com [`search.indexing.includeCodeBlocks`](/docs/configuration/search).
:::

## Uma especificação local [#a-local-spec]

Um caminho relativo é resolvido a partir da raiz do seu projeto e lido durante o build. Funciona tanto com JSON quanto com YAML, e o `blume dev` observa o arquivo, junto com quaisquer [overlays](#overlays) locais, então a referência é atualizada quando você salva a especificação:

```ts blume.config.ts lineNumbers
reference: [openapi({ spec: "./openapi.yaml" })],
```

## OpenAPI 3.2 [#openapi-32]

Especificações OpenAPI 3.2 são renderizadas do jeito que foram escritas. Uma operação `query`, para o método HTTP `QUERY` (uma requisição segura que carrega um corpo), ganha uma página, o Try it e exemplos de código, como qualquer outro método. Campos adicionados na 3.2 que o Blume não exibe, como o `summary` de uma tag ou de uma resposta, são ignorados em vez de rejeitados. Algumas novidades da 3.2 ainda não são renderizadas:

- `additionalOperations`, para métodos que um path item não nomeia diretamente (como `COPY`): essas operações ficam de fora, com um [aviso](#spec-warnings) `BLUME_OPENAPI_UNSUPPORTED`.
- Parâmetros `in: querystring`: eles não ganham linha na tabela de parâmetros, nem campo no Try it, nem lugar nos exemplos de código, e geram o mesmo aviso.
- `itemSchema`, o schema de cada item em um corpo transmitido em streaming (`text/event-stream`, `application/jsonl`): a página não mostra nenhum schema para esse corpo, a menos que `schema` esteja definido ao lado dele.
- Exemplos escritos com `dataValue` ou `serializedValue` no lugar de `value`: a página não os mostra.
- Tags aninhadas (`parent`) e o `kind` das tags: as tags continuam em uma única lista plana na barra lateral e na visão geral.

## Rota [#route]

`route` define onde a referência é montada. Isso vale para a página de visão geral, para o prefixo de todas as rotas de operação e para a rota à qual você aponta uma aba de navegação:

```ts blume.config.ts lineNumbers
reference: [
  openapi({
    route: "/api",   // overview at /api, operations at /api/<tag>/<operation>
    spec: "./openapi.yaml",
  }),
],
```

## Exemplos de código e schemas [#code-samples-and-schemas]

`codeSamples` escolhe quais linguagens são renderizadas em cada operação, na ordem em que você as lista. O padrão é `["curl", "js", "python"]`, e `false` ou uma lista vazia não mostra nenhum. Com `expandSchemas`, as linhas de schemas aninhados começam expandidas em vez de recolhidas:

```ts blume.config.ts lineNumbers
reference: [
  openapi({
    spec: "./openapi.yaml",
    codeSamples: ["curl", "python", "go", "java", "csharp"],
    expandSchemas: true,
  }),
],
```

Cada exemplo é um código simples, pronto para copiar e colar, que faz a requisição com o cliente HTTP padrão ou mais comum da linguagem:

| Id           | Linguagem  | Cliente             | Também aceita         |
| ------------ | ---------- | ------------------- | --------------------- |
| `curl`       | cURL       | `curl`              | `bash`, `sh`, `shell` |
| `python`     | Python     | `requests`          | `py`                  |
| `js`         | JavaScript | `fetch`             | `javascript`          |
| `node`       | Node.js    | `axios`             | `nodejs`, `node.js`   |
| `typescript` | TypeScript | `fetch`             | `ts`                  |
| `php`        | PHP        | a extensão curl     |                       |
| `go`         | Go         | `net/http`          | `golang`              |
| `java`       | Java       | `java.net.http`     |                       |
| `ruby`       | Ruby       | `net/http`          | `rb`                  |
| `powershell` | PowerShell | `Invoke-RestMethod` | `ps1`                 |
| `swift`      | Swift      | `URLSession`        |                       |
| `csharp`     | C#         | `HttpClient`        | `c#`, `cs`            |
| `dotnet`     | .NET       | RestSharp           | `.net`, `dot-net`     |
| `c`          | C          | libcurl             |                       |
| `cpp`        | C++        | cpr                 | `c++`                 |
| `kotlin`     | Kotlin     | OkHttp              | `kt`                  |
| `rust`       | Rust       | reqwest             | `rs`                  |
| `dart`       | Dart       | `package:http`      | `flutter`             |

Cada valor é colocado entre aspas de acordo com as regras da própria linguagem. Assim, um header como `If-Match: "33a64df5"` ou um corpo com um `$` chega à API exatamente como foi escrito.

As tabelas de schema seguem o caminho que os dados percorrem, assim como os exemplos: o corpo de uma requisição deixa de fora as propriedades `readOnly`, que o servidor define, e uma resposta deixa de fora as `writeOnly`, que ele nunca devolve. O corpo de um [webhook ou callback](#webhooks-and-callbacks) é uma requisição que a sua API envia, então ele é tratado como uma resposta.

### Seus próprios exemplos [#your-own-samples]

Para mostrar o seu SDK em vez de uma chamada HTTP crua, adicione `x-codeSamples` a uma operação na especificação. Essa é a extensão definida pela Redocly, e o Speakeasy e o Stainless conseguem gerá-la para você. Cada entrada recebe um `lang`, o `source` e um `label` opcional:

```yaml openapi.yaml lineNumbers
paths:
  /plants:
    get:
      x-codeSamples:
        - lang: typescript
          label: SDK
          source: |
            const plants = await planter.plants.list();
        - lang: bash
          label: CLI
          source: |
            planter list
```

Esses exemplos aparecem em abas próprias, antes dos gerados, e continuam exatamente como foram escritos quando o leitor altera o formulário do [Try it](#try-it-playground). A grafia antiga `x-code-samples` também funciona. Para mostrar só os seus próprios exemplos, defina `codeSamples: false`. Diferente dos exemplos gerados, eles também entram na cópia em Markdown da página da operação, então o `llms-full.txt`, o servidor MCP e o assistente veem as chamadas do seu SDK.

O `source` também pode ser um `$ref` para um arquivo com o código do exemplo, do jeito que a Redocly descreve para manter os exemplos em arquivos próprios. O Blume lê o arquivo de forma relativa à especificação e o baixa quando a especificação é uma URL. Um `$ref` que ele não consegue ler, ou que aponta para dentro de um documento (`#/…`), deixa esse exemplo de fora com um aviso [`BLUME_OPENAPI_CODE_SAMPLE_REF`](#spec-warnings):

```yaml openapi.yaml lineNumbers
paths:
  /plants:
    get:
      x-codeSamples:
        - lang: go
          source:
            $ref: ./code_samples/go/list_plants.go
```

## Playground Try it [#try-it-playground]

As páginas de operação renderizadas nativamente já vêm com um painel interativo **Try it**. O Blume gera o formulário a partir da própria operação. Cada parâmetro de caminho, de query e de header ganha um campo, o editor de corpo é montado a partir do schema do corpo da requisição e tudo vem pré-preenchido com os exemplos da especificação. Os valores são enviados do jeito que a especificação descreve: parâmetros de array e de objeto seguem o `style` e o `explode` deles (`tags=dog&tags=cat` em uma query, `1,2` em um caminho, `filter[color]=red` para `deepObject`), e um corpo `application/x-www-form-urlencoded` ou `multipart/form-data` é enviado como campos de formulário, e não como JSON. Um seletor de servidor lista os servidores da operação (os `servers` dela, senão os do caminho dela, senão os da especificação, com cada `{variable}` no seu `default`) e inclui um campo de texto livre para qualquer outra URL base. Os campos de autenticação seguem a [segurança resolvida](#authorization) da operação: token bearer, chave de API e credenciais basic. Para OAuth2, há um campo onde você cola o token. Você precisa trazer um access token, porque o Blume não executa o fluxo.

O painel e os exemplos de código andam juntos. Os valores digitados no formulário atualizam os exemplos gerados em tempo real, então um comando curl copiado sempre corresponde exatamente ao que o **Send** faria. E o painel não atrapalha: ele é renderizado no servidor já recolhido, e o JavaScript dele só carrega quando um leitor o abre pela primeira vez. Quem nunca mexe no painel não baixa nada disso.

O único método que um navegador não consegue enviar é o `TRACE`, porque o `fetch` se recusa a enviá-lo. Por isso, em uma operação `trace`, o **Send** avisa isso em vez de enviar a requisição, e o exemplo em JavaScript (feito com `fetch`) vira uma nota em vez de código. Os exemplos em cURL e Python enviam normalmente.

Para desligar tudo, basta usar `playground: false`:

```ts blume.config.ts lineNumbers
reference: [openapi({ spec: "./openapi.yaml", playground: false })],
```

### Credenciais [#credentials]

As credenciais digitadas nos campos de autenticação ficam só na memória e somem quando a página é recarregada. Se você marcar **Remember on this device**, elas ficam salvas no `localStorage`, restritas à origem da documentação. Elas nunca são enviadas a nenhum lugar além da API chamada. Os exemplos de código continuam mostrando placeholders (`YOUR_TOKEN` e afins), não importa o que for digitado, a menos que o leitor ative **Include my values in samples**.

### CORS e o proxy [#cors-and-the-proxy]

Assim como em um [embed do Scalar](/docs/references/scalar), as requisições vão **direto do navegador** para a API de destino. Por isso, a API precisa permitir requisições cross-origin vindas do site de documentação (`Access-Control-Allow-Origin`). Se a API não permitir, defina `playground.proxy`. Com uma URL, as requisições passam por um proxy hospedado por você. Com `true`, você ativa a rota nativa `/_api-proxy` (em `{basePath}/_api-proxy` quando você define um [`basePath`](/docs/deployment#mount-the-docs-under-a-path)), que exige [saída de servidor](/docs/deployment#server-rendering), ou seja, um adaptador de hospedagem como `deployment: vercel()` de `blume/deploy`:

```ts blume.config.ts lineNumbers
reference: [
  openapi({
    spec: "./openapi.yaml",
    playground: {
      proxy: true,   // or a URL of your own
    },
  }),
],
```

O proxy nativo só encaminha requisições para as origens declaradas em `servers` nas suas especificações (no nível do documento, do caminho ou da operação, com as variáveis nos seus valores padrão), inclusive quando segue redirecionamentos. Assim, uma documentação publicada não pode ser usada para acessar outros hosts da rede onde ela roda. Uma **Custom base URL** digitada no painel não conta como servidor documentado: com o proxy ativado, as requisições para ela são recusadas com um 403. O proxy só encaminha os headers que o próprio painel define (as credenciais e os parâmetros de header preenchidos, além do `Content-Type` do corpo). Assim, cookies, credenciais que o navegador anexa para o site de documentação (como a autenticação HTTP Basic de um preview protegido por senha) e headers adicionados pela sua hospedagem (`X-Forwarded-For`, `CF-*`, `X-Vercel-*`) nunca chegam à API. O proxy lê o corpo da requisição só até 4 MB, e qualquer coisa maior recebe um `413`. Toda resposta repassada por ele carrega `Content-Security-Policy: sandbox`, `X-Content-Type-Options: nosniff` e `Cross-Origin-Resource-Policy: same-origin`, além de `Content-Disposition: attachment` para HTML ou SVG. Assim, uma página de erro da API que ecoa a entrada não consegue executar scripts na origem da documentação. O proxy também tem [limite de requisições](/docs/configuration/rate-limiting) por leitor, assim como toda rota de servidor que um leitor pode chamar.

## Várias especificações [#multiple-specs]

Use `sources` para publicar mais de uma especificação com um único adaptador. Cada fonte ganha sua própria rota de visão geral e suas próprias páginas de operação, e todas compartilham as opções de exibição do adaptador. Dê um `label` a cada uma (ele nomeia o grupo dela na barra lateral exatamente como está escrito e serve para derivar a rota) ou defina uma `route` explícita:

```ts blume.config.ts lineNumbers
reference: [
  openapi({
    sources: [
      { label: "Public API", spec: "./public.json" },   // → /reference/public-api
      { label: "Admin API", route: "/admin", spec: "./admin.json" },
    ],
  }),
],
```

`spec` é um atalho para um `sources` com uma única entrada, então você só precisa de `sources` quando tiver mais de uma especificação. Se duas especificações precisarem de opções de exibição diferentes, como conjuntos diferentes de exemplos de código, liste dois adaptadores `openapi()`, cada um com sua própria `route`. Para incorporar uma referência do [Scalar](/docs/references/scalar) ao lado das páginas nativas, adicione um adaptador `scalar()` separado na lista. As fontes são resolvidas na ordem da lista. Quando duas resolvem para a mesma rota, a primeira vence, e o build emite um aviso sobre a que foi descartada.

### Indexação por fonte [#per-source-indexing]

Por padrão, as páginas geradas entram na busca, no `llms.txt` e na indexação por crawlers. Uma especificação secundária ou sobreposta pode ficar de fora de qualquer um desses lugares sem esconder suas páginas nem sair da navegação:

```ts blume.config.ts lineNumbers
reference: [
  openapi({
    sources: [
      { label: "Public API", route: "/api", spec: "./public.json" },
      {
        label: "Platform API",
        route: "/platform",
        spec: "./platform.json",
        includeInSearch: false,
        includeInLlms: false,
        noindex: true,
      },
    ],
  }),
],
```

- `includeInSearch: false` tira a visão geral e as operações da fonte da busca do site.
- `includeInLlms: false` tira essas páginas dos dois arquivos `llms.txt`.
- `noindex: true` adiciona metadados de noindex para crawlers e remove as páginas do sitemap.

A meta description de cada página de operação é a `description` (ou o `summary`) da própria operação, seguida de uma frase gerada que cita o endpoint, como "Reference for the `GET /pets` endpoint in the Petstore API.". Assim, mesmo uma especificação com resumos curtos de uma linha gera uma descrição única, do tamanho de um snippet, para cada página. Essa frase é em inglês. Se a prosa da sua especificação estiver em outro idioma, defina `seoDescriptionSuffix: false` na fonte para removê-la. Aí cada página é descrita só com o texto que você escreveu. Uma operação sem `description` e sem `summary` usa o título como fallback (`GET /pets`), então nenhuma página fica com a descrição vazia:

```ts blume.config.ts lineNumbers
reference: [
  openapi({
    sources: [{ spec: "./openapi.de.json", seoDescriptionSuffix: false }],
  }),
],
```

Um embed [`scalar()`](/docs/references/scalar) aceita só a opção `noindex` dentre essas. Ele já fica fora da busca e do `llms.txt` do Blume, então as duas opções `include*` não teriam efeito nele.

## Overlays [#overlays]

Quando a especificação é gerada por outra ferramenta ou pertence a outro time, mantenha as alterações da sua documentação fora dela com um [OpenAPI Overlay](https://spec.openapis.org/overlay/latest.html): um arquivo separado que lista as alterações a serem feitas na especificação, como descrições mais claras, uma URL de servidor pública ou a remoção de operações internas. Liste os overlays ao lado de `spec`. Cada um é um caminho local ou uma URL `http(s)`, e eles são aplicados em ordem:

```ts blume.config.ts lineNumbers
reference: [
  openapi({
    spec: "./openapi.json",
    overlays: ["./overlays/public.yaml"],
  }),
],
```

```yaml overlays/public.yaml lineNumbers
overlay: 1.1.0
info:
  title: Public docs
  version: 1.0.0
actions:
  - target: $.paths.*[?@['x-internal'] == true]
    remove: true
  - target: $.info
    update:
      description: The public Acme API.
```

O `target` de cada ação é uma expressão [JSONPath](https://www.rfc-editor.org/rfc/rfc9535). `update` mescla seu conteúdo em cada nó selecionado: objetos são mesclados chave por chave, arrays ganham os novos itens e os demais valores são substituídos. `copy` mescla um nó vindo de outra parte da especificação (Overlay 1.1), e `remove: true` apaga os alvos. As versões 1.0 e 1.1 da Overlay Specification são suportadas.

Os overlays são aplicados à especificação do jeito que ela foi escrita, antes de o Blume convertê-la para OpenAPI 3.1. Por isso, um overlay tem como alvo a versão em que você escreveu a especificação. Tudo o que é gerado a partir da especificação reflete o resultado: as páginas de operação, a barra lateral, a busca, o `llms.txt` e o servidor MCP. Com `sources`, dê a cada fonte seus próprios `overlays`. Um overlay que não pode ser aplicado faz a referência falhar, assim como acontece com uma especificação ilegível. Assim, um overlay quebrado não consegue publicar o que deveria esconder.

## Autorização [#authorization]

Operações que declaram [requisitos de segurança](https://spec.openapis.org/oas/v3.1.0#security-requirement-object) renderizam uma seção **Authorization** acima dos parâmetros. Os exemplos de código gerados enviam uma credencial placeholder de acordo com o esquema: `Authorization: Bearer YOUR_TOKEN`, um header de chave de API ou uma chave na query. Não há nada para configurar. O Blume lê `security` da especificação, então a referência sempre corresponde ao que a API realmente exige.

A semântica do OpenAPI é mantida exatamente como está escrita:

- O `security` da própria operação substitui o padrão definido na raiz do documento. `security: []` marca a operação como **pública**, e nenhuma seção Authorization é renderizada.
- Várias entradas de requisito são alternativas e aparecem como grupos "ou". Todos os esquemas de uma mesma entrada são exigidos juntos. Os exemplos de código usam a primeira alternativa.
- Uma entrada vazia `{}` significa que a autenticação é **opcional** naquela operação, e a seção avisa isso.
- Os escopos OAuth2 são listados por esquema, e as `description`s dos esquemas em `components.securitySchemes` aparecem inline.

## Webhooks e callbacks [#webhooks-and-callbacks]

As requisições que a sua API envia também são documentadas. Cada [webhook](https://spec.openapis.org/oas/v3.1.0#oas-webhooks) no `webhooks` da raiz da especificação ganha sua própria página, assim como uma operação: ele fica na sua primeira tag ou, quando não tem nenhuma, em um grupo **Webhooks**. A página mostra o schema do payload e as respostas que o seu endpoint deve devolver. No lugar do painel Try it e dos exemplos de código, a coluna lateral mostra um payload de exemplo, já que a sua API envia essa requisição em vez de recebê-la. A página de um webhook lista só o `security` que o próprio webhook declara: o `security` da raiz da especificação protege as chamadas feitas à sua API, então ele não se aplica às requisições que a API envia. Um webhook que é um `$ref` para um path item compartilhado fica de fora, com um aviso [`BLUME_OPENAPI_REF_PATH_ITEM`](#spec-warnings).

```yaml openapi.yaml lineNumbers
webhooks:
  newPet:
    post:
      summary: New pet added
      requestBody:
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/Pet"
      responses:
        "200":
          description: Return a 200 to acknowledge the event.
```

Os webhooks de uma especificação 3.0 que ficam na extensão `x-webhooks` viram `webhooks` quando o Blume converte a especificação para 3.1. Uma especificação que já está na 3.1 ou em uma versão posterior não é convertida, então os webhooks que ela ainda mantém em `x-webhooks` não renderizam nada e geram um aviso [`BLUME_OPENAPI_X_WEBHOOKS`](#spec-warnings): renomeie o campo para `webhooks`.

Os [`callbacks`](https://spec.openapis.org/oas/v3.1.0#callback-object) de uma operação, ou seja, as requisições que a sua API faz de volta para uma URL informada por quem a chamou, são renderizados em uma seção **Callbacks** na página dessa operação. Cada um mostra a expressão de URL (`{$request.body#/callbackUrl}`), o método, os parâmetros (um header de assinatura, por exemplo), o corpo da requisição e as respostas esperadas. Callbacks declarados em `components.callbacks` e referenciados com `$ref` funcionam do mesmo jeito.

As páginas de webhook são páginas reais: elas aparecem na busca, no `llms.txt` e no servidor MCP, e o Markdown delas avisa aos agentes que se trata de uma requisição enviada pela API. Assim, um agente não vai tentar chamá-la.

## Avisos da especificação [#spec-warnings]

O Blume não valida a especificação contra o schema do OpenAPI. Para isso, rode um linter como o [Spectral](https://github.com/stoplightio/spectral) ou o [oasdiff](https://github.com/oasdiff/oasdiff) no CI. Mas ele avisa, no `blume dev`, no `blume build` e no `blume check`, sobre erros que, de outra forma, seriam renderizados errado sem nenhum sinal, e sobre partes da especificação que ele deixa de fora. Cada aviso cita a especificação, e o resto da referência continua sendo gerado:

| Código | O que está errado |
| --- | --- |
| `BLUME_OPENAPI_PATH_PARAMETER_MISSING` | Um `{name}` no caminho de uma operação não tem um parâmetro `in: path` com esse nome. Assim, a página não tem campo para ele, e o Try it e os exemplos de código enviam o placeholder como texto literal. |
| `BLUME_OPENAPI_PATH_PARAMETER_UNUSED` | Um parâmetro `in: path` não tem um `{name}` correspondente no caminho, então o valor que o Try it pede nunca chega à URL. |
| `BLUME_OPENAPI_UNKNOWN_SECURITY_SCHEME` | Um requisito de `security` cita um esquema que `components.securitySchemes` não define. Assim, a seção [Authorization](#authorization) não consegue descrevê-lo, e as requisições não enviam nenhuma credencial para ele. |
| `BLUME_OPENAPI_UNSUPPORTED` | A especificação usa um recurso do [OpenAPI 3.2](#openapi-32) que o Blume ainda não renderiza: `additionalOperations`, que deixa essas operações de fora, ou um parâmetro `in: querystring`, que deixa a query string de fora da página, do Try it e dos exemplos de código. |
| `BLUME_OPENAPI_CODE_SAMPLE_REF` | O `source` de uma entrada de `x-codeSamples` é um `$ref` que o Blume não consegue ler, ou que aponta para dentro de um documento, então esse [exemplo](#your-own-samples) fica de fora. |
| `BLUME_OPENAPI_X_WEBHOOKS` | Uma especificação 3.1 ou posterior mantém os webhooks em `x-webhooks`, a extensão que as ferramentas de 3.0 leem, e não tem `webhooks`, então nenhum deles é renderizado. Renomeie o campo para `webhooks`. |
| `BLUME_OPENAPI_REF_PATH_ITEM` | Um caminho ou webhook é um `$ref` para um path item compartilhado, como um que fica em `components.pathItems`. O Blume não resolve esses casos, então as operações dele ficam de fora da referência. Coloque o path item inline em `paths` ou `webhooks`. Os schemas, parâmetros e respostas dele podem continuar como `$ref`s. |

## Incorporando o Scalar [#embedding-scalar-instead]

`openapi()` sempre renderiza as páginas do próprio Blume. Se você preferir incorporar a UI de referência de API independente do [Scalar](https://scalar.com) em uma única rota, com barra lateral, busca, tema e cliente de requisições próprios, liste um adaptador `scalar()` de `blume/reference` no lugar deste ou ao lado dele. A página do [Scalar](/docs/references/scalar) explica o que o embed faz e o que ele não faz, além de mostrar como repassar as opções do próprio Scalar.
