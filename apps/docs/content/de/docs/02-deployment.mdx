## Überall bereitstellen (statisch) [#deploy-anywhere-static]

`blume build` kompiliert deine Dokumentation zu reinem HTML, CSS und einem lokalen Suchindex in `dist/`. Es muss kein Server betrieben werden — richte einfach einen beliebigen statischen Host auf den Ordner aus.

| Einstellung        | Wert             |
| ------------------ | ---------------- |
| Build-Befehl       | `blume build`    |
| Ausgabeverzeichnis | `dist`           |
| Node-Version       | 22.12 oder neuer |

Diese Einstellungen funktionieren auf Vercel, Netlify, Cloudflare Pages, GitHub Pages oder in jedem Bucket bzw. CDN. Stelle sicher, dass `blume` eine Abhängigkeit ist, damit der Host den Build ausführen kann.

Amazon S3 hinter CloudFront mit einem privaten Bucket, der über Origin Access Control gelesen wird, benötigt zwei weitere Bausteine, da der S3-REST-Endpunkt jeden Schlüssel exakt nachschlägt und jede Datei mit dem Typ ausliefert, mit dem sie hochgeladen wurde:

- Eine CloudFront Function für Viewer-Requests, die jede Seiten-URL der `index.html` zuordnet, die Blume dafür schreibt: `/quickstart` zu `/quickstart/index.html` und `/` (oder jeden Pfad, der auf `/` endet) zu seiner `index.html`. Lass einen Pfad, dessen letztes Segment einen Punkt enthält (`/quickstart.md`, `/_astro/app.js`), unverändert, und halte die Funktion von `/.well-known/*` fern, dessen `api-catalog` keine Dateiendung hat. Ohne sie beantwortet S3 `/quickstart` mit einem `403` oder `404`.
- Uploads, die die Typen setzen, die eine Ableitung aus der Dateiendung falsch ermittelt oder ohne Charset lässt: `text/markdown; charset=utf-8` für `.md` und `.mdx`, `text/plain; charset=utf-8` für `.txt` und `application/linkset+json; profile="https://www.rfc-editor.org/info/rfc9727"` für `.well-known/api-catalog`. `dist/_headers` führt jede Regel auf, die dein Build benötigt.

Der [Leitfaden zu S3 und CloudFront](/guides/s3-cloudfront-documentation-site) enthält eine CloudFormation-Vorlage mit der Funktion und ein Deploy-Skript, das mit diesen Typen hochlädt.

Auf Cloudflare Workers, das einen statischen Build als statische Assets ausliefert, setze `"html_handling": "drop-trailing-slash"` unter `assets` in deiner Wrangler-Konfiguration. Blume schreibt jede Seite als `<route>/index.html` und verlinkt sie ohne abschließenden Schrägstrich, und die Standardeinstellung von Cloudflare (`auto-trailing-slash`) beantwortet `/quickstart` mit einem `307` auf `/quickstart/`. Ein [`cloudflare()`-Server-Build](#server-rendering) leitet jede Seite durch seinen Worker, der `/quickstart` bei beiden Einstellungen ausliefert; dort spielt die Einstellung also nur eine Rolle, wenn der Build mit `Could not wire Accept: text/markdown negotiation` warnt und die statische Ebene die Seiten selbst ausliefert.

Ein statischer Build enthält:

- jede Dokumentations- und benutzerdefinierte Seite als statisches HTML
- einen lokalen Suchindex (standardmäßig Orama, Pagefind optional)
- eine [`sitemap.xml`](/docs/discoverability/sitemap-and-robots#sitemap), wenn die Site-URL bekannt ist
- eine [`robots.txt`](/docs/discoverability/sitemap-and-robots#robots), die auf die Sitemap verweist, wenn die Site-URL bekannt ist
- `llms.txt` und `llms-full.txt` für KI-Tools
- Weiterleitungsseiten
- vorgerenderte [Open-Graph-Bilder](/docs/discoverability/open-graph), wenn `seo.og.enabled` aktiviert ist

### Deine Site-URL festlegen [#set-your-site-url]

Sitemaps, Canonical-Tags, RSS und Open-Graph-Bilder benötigen einen absoluten Origin. Auf **Vercel**, **Netlify** und **Cloudflare Pages** erkennt Blume ihn zur Build-Zeit aus der Umgebung der Plattform — keine Konfiguration erforderlich.

Setze `site` — eine absolute `http://`- oder `https://`-URL —, um den erkannten Wert zu überschreiben oder um auf Hosts, die ihn nicht bereitstellen (GitHub Pages, S3, ein eigenes CDN), einen Wert anzugeben. Bei einem statischen Build ist das das einfache `deployment`-Objekt:

```ts blume.config.ts lineNumbers
deployment: {
  site: "https://docs.example.com",
}
```

Auf Vercel und Netlify bevorzugt die automatische Erkennung deine stabile Produktionsdomain gegenüber Preview-URLs einzelner Deployments, sodass der kanonische Origin über Deployments hinweg gleich bleibt. Cloudflare Pages stellt nur die URL des aktuellen Deployments bereit (`CF_PAGES_URL`), die sich mit jedem Deployment ändert, setze dort also `site`. Cloudflare Workers stellt gar keine bereit, setze `site` also auch auf Workers.

Während `blume dev` fällt die Site-URL auf deinen lokalen Dev-Server zurück (z. B. `http://localhost:4321`), wenn keine gesetzt ist, damit Site-abhängige Funktionen — Open-Graph-Bilder, Canonicals, die Sitemap — sofort funktionieren. Builds verwenden diesen Fallback nie, sodass die Produktionsausgabe niemals auf localhost verweist.

### Monorepos

Stelle den Dokumentations-Workspace als eigenes Projekt bereit, wobei das Stammverzeichnis des Hosts auf ihn gesetzt ist (**Root Directory** bei Vercel, **Base directory** bei Netlify), und verwende die obigen Einstellungen. Lass auf Vercel **Include source files outside of the Root Directory in the Build Step** aktiviert — das ist die Standardeinstellung —, wann immer die Dokumentation Dateien außerhalb ihres Workspace liest: [Komponentenbeispiele](/docs/content/components#component) oder ein Workspace-Paket, das sie importiert, einen `@source`-Pfad in `theme.css` oder eine Spezifikation an anderer Stelle im Repository. Ist die Option deaktiviert, kann der Build diese Dateien nicht erreichen. Der [Monorepo-Leitfaden](/guides/monorepo-documentation-site) führt Schritt für Schritt durch ein Setup mit pnpm und Turborepo.

## Lokale Vorschau [#preview-locally]

Bevor du veröffentlichst, kannst du den Produktions-Build genau so in der Vorschau ansehen, wie ihn ein statischer Host ausliefern würde:

```bash
blume build
blume preview
```

`blume preview` liefert statische Builds sowie Server-Builds mit `node()` und `cloudflare()` aus. Die Adapter für Vercel und Netlify haben keinen lokalen Vorschau-Server, daher bricht der Befehl nach einem Server-Build mit `vercel()` oder `netlify()` stattdessen mit einem Fehler ab. Probiere die Site mit `blume dev` aus oder stelle mit `vercel deploy` bzw. `netlify deploy` eine Vorschau bereit.

## Deployments unter einem Unterpfad [#subpath-deploys]

Du lieferst deine Dokumentation unter einem Pfad wie `example.com/docs` aus? Setze `base` — üblich für GitHub-Pages-Projektseiten. Die gesamte Site, einschließlich der Wurzel, wird unter die Basis verschoben, und interne Links sowie Assets werden so umgeschrieben, dass sie die Basis enthalten.

```ts blume.config.ts lineNumbers
deployment: {
  base: "/docs",
}
```

`base` (und `site`) sind auch Optionen jedes Host-Adapters: `vercel({ base: "/docs" })`. `@astrojs/vercel` ignoriert die Basis, daher verschiebt ein `vercel()`-Server-Build selbst die statischen Dateien nach `.vercel/output/static/docs/` sowie die Routen und Weiterleitungen in `.vercel/output/config.json` unter `/docs`.

Jede Seite behält ihren eigenen Pfad unter der Basis, selbst in einem Inhaltsordner, der denselben Namen wie die Basis trägt: Mit `base: "/docs"` wird `docs/setup.md` unter `/docs/docs/setup` ausgeliefert, und ihre kanonische URL, ihr Seitenleisten-Link und ihr `llms.txt`-Eintrag verweisen dorthin. Ein wurzelrelativer Link, den du schreibst und der bereits mit der Basis beginnt, gilt als Link, der die Basis schon enthält, und bleibt unverändert — verlinke diese Seite also mit einem relativen Link (`./docs/setup`) oder ihrem vollständigen Pfad (`/docs/docs/setup`).

## Die Dokumentation unter einem Pfad einhängen [#mount-the-docs-under-a-path]

`basePath` hängt jede generierte Route unter ein Segment (`/docs/getting-started`), lässt die Seitenleiste dabei aber unverändert — die oberste Ebene sind deine Abschnitte, keine umschließende Gruppe. Verwende es, wenn die Dokumentation unter `/docs/*` liegt, die Site-Wurzel aber dir gehört (wie `routeBasePath` bei Docusaurus oder `baseUrl` bei Fumadocs).

```ts blume.config.ts lineNumbers
basePath: "/docs",
```

Schreibe Links so, als wären sie an der Wurzel eingehängt (`/getting-started`); Blume schreibt sie um — ebenso Weiterleitungen, die Sitemap, kanonische URLs, Open-Graph-Bilder, `llms.txt` und den Suchindex. Öffentliche Assets (Bilder, Dateien unter `public/`) bleiben an der Site-Wurzel bzw. unter [`base`](#subpath-deploys), wenn du eine Basis festlegst.

Dies ist ein anderes Konzept als die beiden obigen Pfade:

- Ein quellenspezifisches [`prefix`](/docs/content/sources#adapters) versieht **eine** Quelle mit einem Namensraum und fügt **sehr wohl** eine Seitenleistengruppe hinzu.
- `deployment.base` ist das Unterverzeichnis des Hosts, aus dem die **gesamte** App ausgeliefert wird. Beide lassen sich kombinieren — sind beide gesetzt, landet eine Seite unter `{deployment.base}/{basePath}/page`.

## Server-Rendering

Statische Ausgabe deckt die meisten Dokumentationen ab. Wechsle zur Server-Ausgabe, wenn du Funktionen zur Anfragezeit benötigst — insbesondere den Endpunkt des [Assistenten](/docs/configuration/assistant) und den [MCP-Server](/docs/discoverability/mcp). Dazu gibst du den Host an: `deployment` nimmt einen aus `blume/deploy` importierten Adapter entgegen.

```ts blume.config.ts lineNumbers
import { defineConfig } from "blume";
import { vercel } from "blume/deploy";

export default defineConfig({
  deployment: vercel(),
});
```

Jeder Adapter akzeptiert dieselben benannten Optionen — `site`, `base` und `output` — und leitet alles Weitere unverändert an den zugrunde liegenden `@astrojs/*`-Adapter weiter, sodass auch eine Option, die Blume nicht selbst benennt, dort ankommt:

```ts blume.config.ts lineNumbers
deployment: vercel({
  site: "https://docs.example.com",
  // Passed straight to @astrojs/vercel.
  isr: { expiration: 60 },
}),
```

| Adapter | Paket | Verwendung für |
| --- | --- | --- |
| `vercel()` | `@astrojs/vercel` | Vercel — der ausgereifteste Weg |
| `netlify()` | `@astrojs/netlify` | Netlify Functions |
| `node()` | `@astrojs/node` | Selbst gehostete Node-Server, Container |
| `cloudflare()` | `@astrojs/cloudflare` | Cloudflare Workers |

`vercel()` und `node()` sind in Blume enthalten — die Auswahl eines der beiden funktioniert einfach. Für `netlify()` und `cloudflare()` muss das jeweilige Paket in deinem Projekt installiert sein (z. B. `bun add -d @astrojs/netlify`). Fehlt es, bricht `blume build` mit dem Installationsbefehl für deinen Paketmanager ab, `blume dev` warnt, und [`blume doctor`](/docs/cli/doctor) meldet es. Mit pnpm musst du außerdem die Build-Skripte, die diese Pakete mitbringen, unter `allowBuilds` in `pnpm-workspace.yaml` freigeben, neben dem `esbuild`-Eintrag, den `blume init` schreibt: `sharp` für Netlify, dessen Adapter eine eigene Kopie mitbringt, und `workerd` für Cloudflare. Ab pnpm 11 bricht pnpm die Installation mit `ERR_PNPM_IGNORED_BUILDS` ab, bis du sie freigibst; pnpm 10 überspringt die Skripte mit einer Warnung. `allowBuilds` erfordert pnpm 10.26 oder neuer.

Die Angabe eines Adapters stellt den Build auf Server-Ausgabe um. Um auf diesem Host einen statischen Build beizubehalten — mit seiner Site-Erkennung und den Plattformdateien, die er liest —, übergib `output: "static"`:

```ts blume.config.ts lineNumbers
deployment: netlify({ output: "static" }),
```

Ein Server-Build enthält alles, was ein statischer Build enthält, sowie alle Astro-Endpunkte oder Middleware, die du hinzufügst. Der `node()`-Adapter erzeugt einen eigenständigen Server, den du direkt mit `node dist/server/entry.mjs` ausführen kannst. Er lauscht auf `localhost:4321`, sofern du beim Start nicht die Umgebungsvariablen `HOST` und `PORT` setzt (`HOST=0.0.0.0 PORT=8080 node dist/server/entry.mjs`); an `node()` übergebene `host`- und `port`-Werte haben keine Wirkung, da `@astrojs/node` sie durch Astros eigene Servereinstellungen ersetzt. Setze hinter einem Reverse Proxy `allowedDomains`, damit die [Ratenbegrenzung](/docs/configuration/rate-limiting#behind-a-reverse-proxy) jeden Leser einzeln zählt. Der Server löst seine Pakete über Links in das `node_modules` deines Projekts auf, deploye das Projekt also mit seinen installierten Abhängigkeiten und nicht nur `dist/`. Wenn die Site Discovery-Dateien veröffentlicht, von einer Inhaltsquelle heruntergeladene Bilder ausliefert oder Weiterleitungen konfiguriert, setzt Blume einen kleinen Wrapper vor den Einstiegspunkt von Astro (der daneben nach `astro-entry.mjs` verschoben wird). Er liefert die `.well-known`-Discovery-Dateien mit ihren Medientypen und CORS-Headern sowie heruntergeladene SVGs in einer Sandbox aus — was der statische Handler des eigenständigen Servers nicht selbst leisten kann — und beantwortet jede Weiterleitung mit ihrem konfigurierten Status.

Ein `cloudflare()`-Server-Build läuft nur auf Cloudflare Workers, da `@astrojs/cloudflare` die Unterstützung für Cloudflare Pages in Version 13 eingestellt hat; ein statischer Build lädt das Paket nicht, daher lässt sich sein `dist/` weiterhin auf Pages deployen. Der Server-Build wird nach `blume build` mit `npx wrangler deploy` aus dem Projektstammverzeichnis deployt: Blume schreibt die umgeleitete Wrangler-Konfiguration nach `.wrangler/deploy/` (und fügt `.wrangler/` zur `.gitignore` hinzu) und benennt den Worker nach deinem Projekt — nach dem `name` aus `package.json`, andernfalls nach dem Hostnamen der Site, andernfalls nach dem Ordner —, sofern nicht eine eigene `wrangler.jsonc` im Projektstammverzeichnis `name` setzt.

Auf Vercel und Cloudflare aktiviert ein Server-Build außerdem die [Content Negotiation über `Accept: text/markdown`](/docs/discoverability/markdown#content-negotiation), sodass ein Agent, der eine beliebige Inhaltsseite mit diesem Header anfragt, unter derselben URL deren Roh-Markdown-Spiegelung erhält. Auf Vercel fügt Blume header-abhängige Rewrites in die Routing-Konfiguration des Deployments ein; auf Cloudflare erzeugt es einen kleinen Worker vor dem Astro-Worker und richtet `assets.run_worker_first` auf jeden Pfad außer den mit Fingerprint versehenen Build-Assets und den rohen `.md`-, `.txt`-, `.json`- und `.well-known`-Dateien aus, da die Plattform andernfalls die vorgerenderten Seiten — und ihre `404.html` für eine URL, hinter der keine Seite steht — ausliefern würde, bevor Servercode ausgeführt wird; diese ausgenommenen Dateien behalten ihren schnellen Pfad ohne Worker. Dieser Worker beantwortet außerdem Anfragen nach den vorgerenderten JSON-Dokumenten pro Seite (`/api/docs/pages/{route}.json`), die bei ihm ankommen, direkt aus dem Asset-Binding, da Astro sie andernfalls an die `/api/`-Catch-all-Route weiterleiten würde.

:::note
`vercel` und `cloudflare` sind auch die Namen zweier [Analytics-Adapter](/docs/configuration/analytics). Wenn eine Konfiguration beide verwendet, vergib für einen der Importe einen Alias: `import { cloudflare as cloudflareDeploy } from "blume/deploy"`.
:::

:::note
Serverfunktionen haben ihre eigene Konfiguration — der Assistent benötigt beispielsweise einen API-Schlüssel für ein Modell. Zur Einrichtung siehe den [Assistenten-Leitfaden](/docs/configuration/assistant).
:::

## Private Dokumentation [#private-docs]

Blume hat keine eigene Anmeldung. Ein statischer Build besteht aus reinen Dateien, und jeder, der den Host erreichen kann, kann alles in `dist/` abrufen. Um eine Site privat zu halten, aktiviere den Zugriffsschutz deines Hosts, der jede Anfrage prüft, bevor eine Datei ausgeliefert wird:

- **Vercel**: [Deployment Protection](https://vercel.com/docs/deployment-protection) mit dem Geltungsbereich **All Deployments**, sodass die Produktion abgedeckt ist und nicht nur Previews. Vercel Authentication lässt Mitglieder deines Vercel-Teams hinein; Password Protection lässt bei kostenpflichtigen Plänen jeden mit einem gemeinsamen Passwort hinein.
- **Netlify**: [Passwortschutz](https://docs.netlify.com/manage/security/secure-access-to-sites/password-protection/) für alle Deployments, mit einem gemeinsamen Passwort oder bei Enterprise-Plänen mit Team-Login.
- **Cloudflare**: [Cloudflare Access](https://developers.cloudflare.com/workers/configuration/cloudflare-access/) auf dem Worker, der die Site ausliefert (**Workers & Pages**, dann dein Worker, dann **Access**), was jede Domain abdeckt, unter der er antwortet. Lege anhand von E-Mail-Adresse, E-Mail-Domain oder Mitgliedschaft im Cloudflare-Konto fest, wer sich anmelden darf.
- **GitHub Pages**: Veröffentliche die Site privat aus einer Organisation auf GitHub Enterprise Cloud, dann können nur Personen mit Lesezugriff auf das Repository sie ansehen.
- **Dein eigener Server**: Setze eine Authentifizierung vor `dist/`, etwa `auth_basic` von nginx oder einen Identity-Aware Proxy.

Der Schutz des Hosts funktioniert bei [Server-Builds](#server-rendering) genauso. Er deckt die gesamte Site ab: Um einige Seiten öffentlich zu halten, veröffentliche sie als separate Site.

Alles, was Blume nach `dist/` schreibt, liegt hinter dem Schutz, darunter Seiten, der Suchindex, die `.md`-Kopien, `llms.txt` und Open-Graph-Bilder. Einige Funktionen reichen über ihn hinaus:

- Ein gehosteter [Suchanbieter](/docs/configuration/search) (Algolia, Orama Cloud, Typesense oder Mixedbread) hält eine eigene Kopie deiner Inhalte bei diesem Dienst vor. Die integrierten Indizes von Orama, FlexSearch und Pagefind sind Dateien in `dist/` und bleiben daher privat.
- Dienste außerhalb des Schutzes können deine Seiten nicht lesen. **Open in chat** übergibt ChatGPT oder Claude einen Link, den sie nicht öffnen können, Linkvorschauen in Slack oder X können deine Open-Graph-Karten nicht anzeigen, und Agenten können weder `llms.txt` noch den MCP-Server lesen. Setze `ai.openInChat: false`, um die Chat-Aktionen auszublenden.

## Weiterleitungen [#redirects]

Ordne alte URLs in `blume.config.ts` neuen zu:

```ts blume.config.ts
redirects: [{ from: "/old", to: "/new", status: 301 }],
```

`status` akzeptiert `301`, `302`, `307` oder `308` (Standard `301`). Server-Builds beantworten Weiterleitungen zur Anfragezeit mit dem konfigurierten Status, ebenso `blume dev`. Statische Builds erzeugen Weiterleitungsseiten **und** die Plattformdateien, die dein Host liest, damit er eine echte HTTP-Weiterleitung ausgibt: `_redirects` für `netlify()` und `cloudflare()`, `vercel.json` für `vercel()` und — wenn kein Host angegeben ist — beide sowie `blume-redirects.json`, ein strukturiertes Manifest für alles Übrige (nginx-/Apache-Regeln, ein Edge Worker). Eine `_redirects` oder `vercel.json`, die du in `public/` mitlieferst, bleibt unangetastet.

Eine Weiterleitung, die eine Seite auf eine andere verschiebt, nimmt das [Roh-Markdown](/docs/discoverability/markdown#raw-markdown) der Seite mit: `/old.md` und `/old.mdx` leiten mit demselben Status auf `/new.md` und `/new.mdx` weiter, in `blume dev` und in jedem Build.

Zwei Hosts benötigen mehr als die Datei:

- **Netlify** liefert eine vorhandene Datei vor einer Weiterleitungsregel aus, sofern die Regel nicht erzwungen wird, und ein statischer Build hat an jedem `from` eine Weiterleitungsseite. Die `_redirects` für `netlify()` erzwingt ihre Regeln (`/old /new 301!`). Cloudflare lehnt dieses Flag ab, daher lässt die Datei, die ein Build ohne angegebenen Host schreibt, es weg, und auf Netlify antwortet dieser Build stattdessen mit der Weiterleitungsseite; gib den Host mit `netlify({ output: "static" })` an, um die HTTP-Weiterleitung zu erhalten.
- **Vercel** liest `vercel.json` aus dem Stammverzeichnis des Projekts, nie aus dem Ausgabeverzeichnis, daher gilt die Kopie in `dist/` nur, wenn du genau diesen Ordner mit der Vercel CLI deployst (`vercel deploy dist`). Ein mit Git verbundenes Projekt liest sie nie: Es liefert die Weiterleitungsseiten und keinen der Header aus [Inhaltstypen](#content-types) aus. Kopiere die `redirects` und `headers` aus `dist/vercel.json` in die `vercel.json` im Stammverzeichnis deines Projekts oder verwende `vercel()` für einen Server-Build, dessen Routing-Konfiguration die Weiterleitungen und die Discovery-Header enthält.

:::note
Schreibe sowohl `from` als auch `to` so, als wären sie an der Wurzel eingehängt, beginnend mit `/` (`to` kann auch eine vollständige `https://`-URL sein) — sowohl unter [`base`](#subpath-deploys) als auch unter [`basePath`](#mount-the-docs-under-a-path) schreibt Blume beide Seiten für dich um, sodass eine Weiterleitung innerhalb der Basis landet. Ein `to`, das auf eine Datei in `public/` verweist (`/files/guide.pdf`), erhält `base`, aber nicht `basePath`, da die Datei dort ausgeliefert wird. Eine Basis, die du bereits von Hand in `to` geschrieben hast, bleibt erhalten und wird nicht verdoppelt.
:::

### Musterbasierte Weiterleitungen [#pattern-redirects]

Ein `from` kann viele Pfade auf einmal abdecken und wird so geschrieben, wie Mintlify und `vercel.json` es tun:

```ts blume.config.ts
redirects: [
  { from: "/beta/:slug*", to: "/v2/:slug*" },
  { from: "/blog/:slug", to: "/articles/:slug" },
  { from: "/articles/concepts-*", to: "/concepts" },
  { from: "/old/article-*", to: "/new/article-*" },
],
```

- `:name` passt auf genau ein ganzes Segment: `/blog/:slug` deckt `/blog/hello` ab, nicht aber `/blog/a/b`.
- `:name*` als letztes Segment passt auf den Rest des Pfads, mit beliebig vielen Segmenten: `/beta/:slug*` leitet `/beta/guides/setup` nach `/v2/guides/setup` weiter und `/beta` selbst nach `/v2`. Ein letztes Segment `*` bewirkt dasselbe.
- `*` am Ende eines Segments passt auf den Rest des Pfads ab dieser Stelle: `/articles/concepts-*` deckt `/articles/concepts-overview` ab.

`to` liest einen erfassten Wert über seinen Namen als ganzes Segment (`/:slug*`, `/:slug`) oder über ein `*` für das, worauf das `*` in `from` gepasst hat (auch `:splat`, die Schreibweise von `_redirects`, liest ihn). Ein `to`, das keinen erfassten Wert liest, leitet jeden Pfad, den das Muster abdeckt, auf eine einzige Seite weiter. Eine exakte Weiterleitung hat Vorrang vor einem Muster, das denselben Pfad abdeckt, und Muster werden in der Reihenfolge ausprobiert, in der du sie aufführst.

Jeder Host erhält die Muster in seiner eigenen Syntax: Splats in `_redirects`, `path-to-regexp`-Quellen in `vercel.json` und in der Routing-Konfiguration eines `vercel()`- oder `netlify()`-Server-Builds. Die Server von `node()` und `cloudflare()` gleichen sie selbst ab, ebenso `blume dev`. Ein statischer Build schreibt für ein Muster keine Weiterleitungsseite, da er eine für jeden Pfad bräuchte, den das Muster abdeckt; ein Host, der keine dieser Dateien liest (etwa GitHub Pages), wendet daher nur die exakten Weiterleitungen an; `blume-redirects.json` führt die Muster so auf, wie du sie geschrieben hast.

Ein Muster darf nicht zugleich auf eine Seite passen: Hosts sind sich uneinig, welche der beiden antwortet, daher bricht der Build mit `BLUME_REDIRECT_MATCHES_PAGE` ab und nennt die Seite. Grenze das Muster auf die Pfade ein, die verschoben wurden. Eine exakte Weiterleitung von der eigenen URL einer Seite antwortet auf jedem Host gleich und übernimmt die URL, sodass die Seite nie veröffentlicht wird; derselbe Code ist dort daher eine Warnung: Lösche die Seite, falls sie verschoben wurde, oder entferne die Weiterleitung.

## Inhaltstypen [#content-types]

Wo der Host eine solche Datei liest, erzeugt ein Build außerdem eine `_headers`-Datei, die `charset=utf-8` an die rohen, KI-tauglichen Endpunkte heftet — `/<route>.md`, `/<route>.mdx` und die `.txt`-Dateien (`llms.txt`, `llms-full.txt`). Diese Antworten sind gültiges UTF-8, doch viele statische Hosts liefern sie als `text/markdown` / `text/plain` **ohne** Charset aus, und Browser fallen dann auf Windows-1252 zurück — sodass Dokumentation mit Nicht-ASCII-Zeichen (Japanisch, akzentuiertes Latein, …) beim direkten Öffnen der Roh-URL als Zeichensalat dargestellt wird. HTML-Seiten sind davon nicht betroffen, da sie `<meta charset>` mitführen. Netlify liest `_headers` bei einem statischen Deployment und Cloudflare (Pages sowie statische Assets von Workers) sowohl bei statischen als auch bei Server-Builds, daher erhalten diese Adapter und ein nicht angegebener statischer Host die Datei; Vercel (dessen Header über die Routing-Konfiguration laufen) und Node (dessen Server die Datei ignoriert) nicht. Ein Netlify-Server-Build schreibt dieselben Regeln stattdessen in die `headers` seiner Frameworks-API-Konfiguration (`.netlify/v1/config.json`). Ein statischer Vercel-Build schreibt dieselben Regeln stattdessen in `dist/vercel.json`, die ein mit Git verbundenes Projekt nicht liest (siehe [Weiterleitungen](#redirects)). Eine `_headers`-Datei, die du in `public/` mitlieferst, bleibt unangetastet.

## Umgebungsvariablen [#environment-variables]

Wenn eine Funktion ein Secret benötigt, warnt Blume bei `blume dev`/`build`, falls es fehlt — so tritt das Problem früh zutage statt erst bei der ersten Anfrage:

| Funktion | Variable |
| --- | --- |
| Assistent (AI Gateway) | `AI_GATEWAY_API_KEY` (oder Vercel OIDC) |
| Assistent (andere Adapter) | die Standard-Schlüssel-Umgebungsvariable des Adapters (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, `XAI_API_KEY`, `OPENROUTER_API_KEY`, `LLMGATEWAY_API_KEY`, `INKEEP_API_KEY`) oder das `apiKeyEnv`, das du ihm übergeben hast |
| [Bot-Schutz des Assistenten](/docs/configuration/assistant#bot-protection) | `TURNSTILE_SECRET_KEY` (`turnstile()`), `HCAPTCHA_SECRET_KEY` (`hcaptcha()`) |
| [Ratenbegrenzung](/docs/configuration/rate-limiting) (`upstash()`) | `UPSTASH_REDIS_REST_URL` und `UPSTASH_REDIS_REST_TOKEN` |
| Mixedbread-Suche | `MIXEDBREAD_API_KEY` |
| [Sprachausgabe](/docs/configuration/narration) (generierte Stimmen) | `AI_GATEWAY_API_KEY` (oder Vercel OIDC) oder das `apiKeyEnv`, das du `gateway()` übergeben hast |
| [Inhaltsquellen](/docs/content/sources) | `NOTION_TOKEN` (`notion()`), `SANITY_TOKEN` (`sanity()`), `CONTENTFUL_ACCESS_TOKEN` (`contentful()`, dazu `CONTENTFUL_PREVIEW_TOKEN` für `--preview`, das ohne ihn fehlschlägt), `PAYLOAD_API_KEY` (`payload()`), `STRAPI_API_TOKEN` (`strapi()`), `GITHUB_TOKEN` (`githubReleases()` sowie `mdxRemote()` beim Lesen aus GitHub) |

Setze sie in `.env.local` für die lokale Entwicklung und in der Umgebung deines Hosts für die Produktion. Eine Inhaltsquelle liest ihr Token beim Abrufen, also während `blume dev` und `blume build`, und die Sprachausgabe liest ihren Schlüssel während `blume build`, setze diese daher dort, wo deine Site gebaut wird. Build-Zeit-Secrets für die Synchronisierung des Suchindex (`ALGOLIA_ADMIN_API_KEY`, `ORAMA_PRIVATE_API_KEY`, `TYPESENSE_ADMIN_API_KEY`) prüft der Sync-Schritt selbst: Ist eines nicht gesetzt, warnt der Build und überspringt die Synchronisierung; ist es gesetzt, [lässt eine fehlgeschlagene Synchronisierung den Build fehlschlagen](/docs/configuration/search#adapters). Die [GitHub-Info](/docs/content/components#github-info)-Karte sendet außerdem `GITHUB_TOKEN`, sofern gesetzt, um die API-Ratenbegrenzung von GitHub anzuheben.

## Build-Cache [#build-cache]

Blume verwendet zwei Caches, die ein Build wiederverwenden kann. Die Caches von Astro und Vite liegen unter `.blume/.cache/` (darunter der Content Store und die Bildtransformationen). Gerenderte [OG-Karten](/docs/discoverability/open-graph#card-cache) liegen in `node_modules/.cache/blume/og`, sodass ein erneuter Build nur die Karten rendert, deren Titel, Beschreibung oder Branding sich geändert hat. Ob eine Plattform dieses Verzeichnis zwischen Deployments behält, ist unterschiedlich:

- **Vercel** stellt `node_modules/**` aus seinem Build-Cache wieder her, sodass Karten erhalten bleiben (der Cache ist 1 GB groß, wird einen Monat lang aufbewahrt und ist pro Branch getrennt — ein neuer Branch startet mit dem Produktions-Cache).
- **Netlify** stellt `node_modules` wieder her, sodass Karten erhalten bleiben.
- **Cloudflare Workers Builds** speichert nur Caches des Paketmanagers und, bei einem erkannten Astro-Projekt, `node_modules/.astro` — niemals `node_modules/.cache` —, sodass dort bei jedem Deployment jede Karte neu gerendert wird.
- **GitHub Actions** und andere Runner, die du selbst verwaltest, behalten nichts, es sei denn, du cachst das Verzeichnis selbst:

```yaml
- uses: actions/cache@v6
  with:
    path: node_modules/.cache/blume/og
    key: blume-og-${{ runner.os }}-${{ hashFiles('**/bun.lock', '**/package-lock.json', '**/pnpm-lock.yaml') }}
    restore-keys: blume-og-${{ runner.os }}-
```

Karten werden anhand ihres Inhalts identifiziert, daher ist ein ungenauer Schlüssel kein Problem: Ein wiederhergestellter Cache spart immer nur Render-Vorgänge und liefert nie eine falsche Karte aus.

Ein Installationsbefehl verwirft den Cache auf jeder Plattform: `npm ci` löscht `node_modules` vor der Installation. Verwende weiterhin `npm install`, `bun install` oder `pnpm install` als Installationsbefehl, um von der Wiederverwendung zu profitieren.

## Build-Zusammenfassung [#build-summary]

Jeder Build gibt eine Zusammenfassung aus — Ausgabemodus, Adapter, aufgelöste Site-URL, Suchanbieter, Anzahl der Weiterleitungen, Status von Sitemap und `llms.txt` sowie alle aktivierten Serverfunktionen — damit du vor dem Deployment prüfen kannst, was ausgeliefert wurde (einschließlich aller automatisch erkannten Werte).
